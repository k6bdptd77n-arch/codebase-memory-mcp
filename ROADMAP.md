# MindForge — дорожная карта: 10 шагов вперёд

*Дата: 2026-07-06 · ветка `fablize-integration` · документ синтезирован из двух независимых
исследований (продуктовый ландшафт середины 2026 + техническая трассировка стека) и полного
аудита/ремонта сессии 2026-07-06.*

**Что уже сделано до этого документа** (коммиты `365c71b…c475959`): атомарные записи всего
состояния `.fablize/`; crew-цикл не клинит на merge-конфликтах и не чекпоинтит не ту историю;
настраиваемый verify-гейт; GUI: hardening (sandbox, IPC-валидация, секреты MCP), устойчивость
к битому состоянию, реальный дифф в ревью, телеметрия полос, **переключатель проектов и мастер
создания проекта/плана**; установщик с `--with-crew/--with-ui/--with-economy`; CI расширен;
123 Python-теста зелёные. Хотфикс: первый коммит при создании проекта (без него `git worktree
add … HEAD` падал в свежем репозитории — первая история была мертва по прибытии).

## Стратегический тезис

**Рынок (факты середины 2026).** Все сошлись к одной форме: план → параллельные агенты в
git-worktree → дифф → merge. Гиганты соревнуются в масштабе и облаке: Cursor Cloud Agents
(10–20+ агентов в облачных VM), OpenAI Codex (облачные агенты + Automations, ~$100–200/мес),
Claude Code Dynamic Workflows (до 1000 субагентов, управляемые агенты с Dreaming/Outcomes).
Локальные worktree-раннеры (Claude Squad, Conductor, Vibe Kanban) — оркестрация без графа,
без мозга, без настоящего гейта. **Ключевой факт, который организует весь роадмап: узкое
место 2026 — не генерация кода, а ёмкость верификации.** Доверие к точности ИИ упало до 29%
(Stack Overflow 2025); индустриальный нарратив — «агенты врут о своей работе».

**Клин MindForge — пересечение, которое облачные гиганты структурно не займут** (оно
подрывает их metered-cloud выручку):

> **Полностью локально · на CLI-подписке, за которую ты уже платишь · не мержит, пока
> тесты не зелёные · помнит между сессиями · ведёт агентов по детерминированному графу
> 158 языков, а не по grep.**

Ни один конкурент не держит все пять осей сразу.

**Заголовок продукта:**
> *MindForge превращает CLI кодинг-агента, за который ты уже платишь, в локальную команду
> с памятью: планирует, строит в параллельных git-worktree и мержит только когда твои
> тесты прошли.*

Короткий вариант (сплэш/соцсети): *«Автономный кодинг, которому можно верить —
локально, на твоей подписке, гейт на зелёных тестах».*

**Чего сознательно НЕ делаем** (проигрышные ходы): гонка за числом агентов и облачными VM;
свой LLM или модель-ревьюер; hosted-SaaS сейчас; переписывание fablize в C; 3D-граф как
украшение. Переименование продукта не делаем — коллизии имени компенсирует тэглайн.

## Шаг 1 — Боеготовность на чужих проектах + первый живой пилот (M)

**Цель.** История, запущенная в любом свежесозданном или открытом проекте, доходит до
worktree, агента и verify-гейта без ручной настройки терминалом.

**Почему.** Трассировка пути исполнения (`story-run` → `orchestrate.py` → worktree →
`claude -p` → review → approve) вскрыла пять конкретных дефектов, из-за которых «любой
проект» сейчас — обещание, а не факт. Всё остальное в роадмапе — теория, пока цикл не
прожит вживую на настоящем проекте.

**Задачи.**
1. ~~Свежий репозиторий без коммитов убивает первую историю~~ — **сделано хотфиксом**
   (`projectcore.js`: первый коммит после дисциплин). Добавить вторую половину: в
   `orchestrate.py run_story` детект unborn HEAD (`git rev-parse --verify HEAD` падает) →
   `git commit --allow-empty` перед `worktree add` — покрывает случай «открыл существующую
   пустую папку с git init».
2. **PATH в GUI-приложении**: запущенное из Finder/дока приложение получает урезанный
   `PATH` (`/usr/bin:/bin`) — `claude`, `python3`, `git` не находятся. В `main.js` при
   старте: дополнить PATH (`/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`,
   npm-global), зарезолвить абсолютные пути трёх бинарей один раз; если `claude` не найден —
   громкий баннер в UI с инструкцией, а не тихий провал запуска.
3. **Allowlist агента шире Python/Node/Go/Rust**: `AGENT_ALLOW` (`orchestrate.py:144`)
   дополнить `pnpm`, `yarn`, `poetry run`, `deno test`, `dotnet test`, `mvn`, `gradle`,
   `bundle exec`, `rspec`, `composer`, `php` + сделать расширяемым полем `hand.allow` в
   per-project `crew.json`. Без этого агент в реальном стеке не может сам прогнать тесты —
   история выглядит проваленной при верном коде.
4. **Гейт crew для чужого проекта**: `DEFAULT_VERIFY = pytest fablize/tests` осмыслен
   только в этом репо. `verify_cmd()` в `mindforge_crew.py`: если путь отсутствует —
   автодетект (`package.json` → `npm test`; `pyproject.toml`/`pytest.ini` → `pytest`;
   `go.mod` → `go test ./...`; иначе честный режим «review-only, гейта нет» с явной
   записью в леджер) вместо гарантированного провала.
5. **Фиксация базы мержа**: при `run_story` сохранять base-sha в состоянии истории;
   `story-approve` (`main.js:449`) предупреждает, если текущий HEAD ушёл от базы
   (пользователь переключил ветку между запуском и одобрением).
6. **Живой пилот**: создать через мастер реальный мини-проект (например, CLI-утилита или
   маленький web-сервис), план из 2–3 историй с verify-командами → прогон → ревью диффа →
   merge. Всё, что заскрипело, — фиксировать как issues; это входные данные для шагов 2–7.

**Критерий готовности.** Новый тест в `test_orchestrate.py`: репо после `git init` без
коммитов + stub-агент → worktree создан, история исполняется. Пилот: ≥2 истории смержены
через GUI без единой команды в терминале; список замечаний оформлен.

**Риски.** PATH-приёмы платформозависимы (mac/linux различаются). Пилот вскроет новые
дефекты — это его назначение, закладывать время на ремонт.

## Шаг 2 — Честный e2e-самотест цикла + защита от дрейфа ядра (M)

**Цель.** CI на каждом PR доказывает две вещи: (а) цикл **не мержит** историю с красным
verify (класс отказа G002), (б) C-ядро осталось байт-в-байт upstream.

**Почему.** Сейчас честность гейта нигде не проверяется по-настоящему:
`test_crew_cycle.py` мокает `run_verification` целиком — то единственное, что больше
всего нуждается в реальной проверке, заглушено. Stub-механизм уже есть
(`--claude-cmd <стаб>`, используется в `test_orchestrate.py:149`) — недостаёт только
негативных сценариев. Инфраструктура доверия обязана сама жить под гейтом, который продаёт.

**Задачи.**
1. `fablize/tests/test_e2e_loop.py` (stdlib unittest, git-gated), три сценария на
   scratch-репозитории и настоящем `mindforge_tools` (без моков):
   - **позитив**: stub-агент пишет файл + коммитит → `review` → `run_verification("true")`
     → `goals_checkpoint(complete)` → `merge_story`; asserts: ветка смержена, worktree
     удалён, `goals.json` complete;
   - **негатив (G002)**: то же, но `run_verification("false")` → история `failed`,
     `merge_story` НЕ вызван, ветка и worktree живы;
   - **конфликт**: две истории в один файл → `merge_story` возвращает `MERGE CONFLICT`,
     дерево чистое (нет `MERGE_HEAD`), ветка цела.
2. Job в `fablize-ci.yml` после существующего unittest-шага (та же матрица 3.9/3.11/3.13).
3. `tools/check-upstream-sync.sh` (лежит вне C-дерева, которое проверяет):
   `git fetch upstream && git diff --quiet upstream/main -- src internal tests pkg tools
   vendored scripts Makefile.cbm install.sh install.ps1 server.json`; при дрейфе —
   ненулевой exit + `--stat`. Отдельный job в `fablize-ci.yml`.

**Критерий готовности.** Оба job зелёные в матрице; локальная порча файла в `src/` →
sync-чекер краснеет; удаление негативного assert'а → ревьюер обязан заметить (тест мутации
вручную).

**Риски.** Низкие — вся git-механика уже отработана в существующих тестах.

## Шаг 3 — Память для каждого проекта: индексация движком из GUI (M)

**Цель.** Создал или открыл проект → граф кода уже строится в фоне; кнопка «Переиндексировать»;
в шапке — живые числа графа (nodes/edges, когда индексирован).

**Почему.** Сейчас **ничего** не индексирует проект, созданный или открытый в GUI:
`layers()` (`main.js:148`) находит проект в `list_projects` по `root_path` — для нового
проекта это `graph: null`, слой Memory мёртв. При этом C-бинарь уже умеет всё нужное:
`BIN cli index_repository '{"repo_path":…,"mode":"fast"}'` (+ `index_status`,
`list_projects`, `delete_project`). Слой Memory — половина ценности стека, и для новых
проектов она сейчас выключена.

**Задачи.**
1. `main.js`: после `createProjectAt`/`switchProject` — фоновый вызов
   `BIN cli index_repository {mode:"fast"}` (не блокировать UI; прогресс в статусбар).
2. Новый IPC `mf.reindex()` (preload + main) + кнопка в статусбаре; по завершении —
   refresh `layers()`.
3. Карточка Memory в шапке: nodes/edges + «индексирован N минут назад» из `index_status`.
4. *(Отложимо внутри шага)* Lifecycle 3D-сервера: запуск `BIN --ui --port 9749` для
   текущего проекта, чтобы существующая кнопка «Открыть 3D-граф» гарантированно попадала
   в граф именно этого проекта.

**Критерий готовности.** Интеграционный тест (skip, если BIN не собран): scratch-репо →
index → `list_projects` содержит его с `nodes>0`; в GUI новый проект показывает числа
графа без ручных действий.

**Риски.** Индексация большого репо длится — нужен прогресс и возможность отмены; режим
`fast` по умолчанию.

## Шаг 4 — Шкала доверия и квитанции мержа (M)

**Цель.** Новичок стартует в режиме MANUAL и по накопленным доказательствам осознанно
поднимается до AUTO-ON-GREEN; каждый merge оставляет экспортируемую «квитанцию».

**Почему.** Это прямой ответ на главную боль рынка («агенты врут», доверие 29%): доверие
нельзя попросить — его надо дать заработать. Квитанция — артефакт, который разработчик
показывает тимлиду; это «прайсинг доверия» в UX. Сейчас crew фактически всегда авто-мержит
при COMPLETE, ручной путь — всегда ручной; явной шкалы нет.

**Задачи.**
1. Три режима в per-project `crew.json` + переключатель в шапке UI:
   - **MANUAL** — каждый merge только рукой из review-drawer;
   - **REVIEW-REQUIRED** — LLM-ревью обязательно, merge рукой;
   - **AUTO-ON-GREEN** — `cycle()` мержит сам при вердикте COMPLETE **и** зелёном verify.
   `mindforge_crew.cycle()` читает режим и в MANUAL/REVIEW останавливается на «готово к
   ревью» вместо мержа.
2. **Квитанция мержа** (`.fablize/receipts/GXXX.md` + `.json`), генерируется в обоих путях
   (`main.js story-approve` и `mindforge_tools.merge_story`): дифф (stat + первые N строк),
   точные verify-команды и их вывод, вердикт ревьюера, sha до/после, длительность (+
   стоимость после шага 5).
3. Кнопка «Экспорт квитанции» в review-drawer; образец квитанции — в README.
4. Расширить e2e-тест шага 2: в AUTO-режиме красный verify не мержится; в MANUAL crew
   не мержит даже зелёное.

**Критерий готовности.** Merge в любом режиме создаёт квитанцию; тесты режимов зелёные;
образец в README собирается из реального прогона.

**Риски.** Не раздувать: квитанция — это файл, а не система отчётности.

## Шаг 5 — Экономика: стоимость, тренды, бюджеты (M)

**Цель.** Вкладка Metrics отвечает на «сколько это стоило и что сэкономило», автономный
`cycle()` физически не может прожечь бюджет.

**Почему.** Весь учёт уже написан и **не подключён**: `imba/hermes-economizer` имеет
прайс-таблицу моделей, ledger, `spent(window)` и `over_budget` c блокировкой — но живёт
только как hook-плагин; `orchestrate.py` запускает `claude -p` без `--output-format
stream-json`, теряя usage; UI считает elapsed per-story и выбрасывает. «Дёшево» — третье
слово ценностного предложения, и оно пока не измеряется.

**Задачи.**
1. `orchestrate.py run_story`: писать в события `duration_s`; если CLI отдаёт JSON-result
   с usage (для claude — включить `stream-json`) — `input_tokens`, `output_tokens`,
   `cost_usd` через `economizer.estimate_cost` (импорт мягкий, деградация без него).
2. `metrics.py`: суммы cost/time по проекту и по историям, тренд last-N прогонов,
   поля в `--json`; подкоманда `summary --week` → markdown-сводка («смержено N историй,
   first-pass verify M%, потрачено $X, сэкономлено ~Y токенов против file-by-file»).
3. `views/metrics.js`: строка стоимости + простые спарклайны (первичный проход verify,
   time-to-green, стоимость/день). Данные уже текут через IPC `metrics`.
4. `mindforge_crew.cycle()`: перед каждой историей `over_budget(load_config())` → стоп
   с итогом в леджер и явным сообщением.
5. Отразить бюджет в Settings (лимит $/день на проект).

**Критерий готовности.** Unit: `metrics --json` содержит cost-поля; `cycle()`
останавливается при застабленном `over_budget=True`; после 3+ прогонов в UI виден тренд.

**Риски.** Форматы usage различаются между CLI — парсить оборонительно, всё опционально.

## Шаг 6 — Секреты и модель угроз (S)

**Цель.** Ни одного plaintext-ключа на диске; одна страница честно объясняет, что агентам
можно, что нельзя и почему код не покидает машину.

**Почему.** Продавать «слой доверия» с ключами в открытом виде нельзя — команды
разворачиваются на этом месте. `safeStorage` Electron уже импортирован и не используется.
Ключи в `.fablize/crew.json` не попадают в git (ignored), но лежат открыто на диске.

**Задачи.**
1. `main.js crewSave`: непустой `providers.*.key` → `{enc: base64(safeStorage.encryptString(key))}`
   при `isEncryptionAvailable()`; `crewLoad` детектит обе формы (обратная совместимость),
   расшифровывает в память, прозрачно перешифровывает при следующем сохранении. `apiChat`
   держит расшифрованное только в памяти.
2. Linux без keyring: честный fallback (plaintext + жёлтое предупреждение в Settings).
3. `THREAT-MODEL.md` (или раздел в fork-части SECURITY.md): 100% локально; seeded
   allowlist worktree-агентов (нет push, нет произвольной сети, нет bypass); что именно
   может исполнить агент; где лежат и как шифруются ключи; что делает квитанция.

**Критерий готовности.** Тест: после сохранения ключа plaintext-строка отсутствует в
`crew.json`; старый plaintext-ключ читается и апгрейдится; страница угроз ссылается из
README и Settings.

**Риски.** Минимальные; аккуратно с миграцией существующих конфигов.

## Шаг 7 — Плагинные «руки» и библиотека verify-рецептов (M)

**Цель.** Истории исполняет любой установленный CLI (claude / codex / gemini / opencode /
aider), а мастер плана предлагает готовые verify-команды под стек проекта.

**Почему.** Ось клина «bring-your-own-CLI» удесятеряет аудиторию (держатели Codex/Gemini
подписок) — и seam уже построен: `orchestrate.py agent_cmd(--agent-style)`,
`roles.hand.cli` в crew.json, сегмент выбора CLI в Settings. Осталась таблица вместо
if/elif и два стиля. Вторая половина: гейт силён ровно настолько, насколько verify-команды —
библиотека рецептов снимает главный авторский барьер мастера плана. Пакеты — plain-text,
это самая дешёвая поверхность для вклада сообщества.

**Задачи.**
1. `orchestrate.py`: `STYLES = {style: {argv_template, permission_flag}}` + `gemini`,
   `opencode`; `choices` argparse и сегмент `settings.js` — из одной таблицы.
2. `cliAvailable` в UI ← детект установленных агентов из C-матрицы установщика (~12 CLI
   уже детектится) — предлагать только то, что реально стоит.
3. `test_agent_style_adapters`: два новых стиля.
4. `fablize/packs/recipes/`: verify-рецепты по стекам — node (npm/pnpm/yarn), python
   (pytest/poetry), go, rust, next.js, deno; каждый: команда тестов, команда сборки,
   allowlist-дополнения.
5. Мастер плана: селект «стек» → префилл verify-команд из рецепта; в Settings — «применить
   рецепт к проекту».
6. CONTRIBUTING: приглашение к PR рецептов и паков.

**Критерий готовности.** Одна история доведена до merge вторым CLI (не claude) на пилотном
проекте; мастер префиллит verify для node- и python-проекта; тесты стилей зелёные.

**Риски.** Семантика permission-флагов у CLI различается — проверять на реально
установленных; не обещать стили, которые не тестировались.

## Шаг 8 — Упаковка: подписанное приложение + релизный CI (L)

**Цель.** Незнакомый разработчик делает double-click на `.dmg`/`.AppImage` и доходит до
работающей доски без терминала.

**Почему.** Блокер принятия №1: сейчас стек собирается только 6-командной установкой из
клона. Три конкретные дыры: (1) упакованное приложение не найдёт свои движки —
`INSTALL = path.resolve(__dirname, "..")`, а `files` electron-builder не включает
`fablize/`, `crew/` и C-бинарь; (2) подписи нет — Gatekeeper заблокирует; (3) UI
отсутствует в релизном CI (release.yml — только upstream-C).

**Задачи.**
1. `package.json build.extraResources`: `fablize/`, `crew/`, собранный BIN;
   `main.js`: `INSTALL` → `process.resourcesPath` при `app.isPackaged`.
2. mac: `hardenedRuntime` + entitlements (спавн дочерних процессов), notarize через
   env-креды (для беты допустим ad-hoc); linux: AppImage + cosign-подпись (подход уже
   есть в release.yml C-ядра — переиспользовать).
3. Новый `.github/workflows/mindforge-release.yml`: matrix macos+ubuntu,
   `npm ci && npm run dist`, артефакты в GitHub Release по тегу `v*`;
   `paths: mindforge-ui/**` — fork-owned, upstream-merge не конфликтует.
4. Первый запуск: welcome-экран — проверка `claude`/движка с человеческими инструкциями,
   выбор/создание первого проекта (использует PATH-hardening шага 1).
5. Однострочник поверх `install-combined.sh` + Homebrew cask (formula → скрипт).

**Критерий готовности.** На чистом пользователе macOS: `.dmg` из Releases → Applications →
запуск → создание проекта → демо-история бежит. `npm run dist` воспроизводим в CI.

**Риски.** Notarization требует Apple Developer ID (платный) — этапность: ad-hoc для беты,
нотариат к v0.2; вес бандла с C-бинарём (~сотни МБ) — вариант «скачать движок при первом
запуске» как fallback.

## Шаг 9 — Позиционирование, демо и двуязычие (M)

**Цель.** Продукт объясняет себя за 3 минуты: hero-строка, сравнительная таблица,
встроенное демо в один клик, видео; EN — язык внешней поверхности, RU — полноправная локаль.

**Почему.** Пока README ведёт с «Memory + Procedure + Brain» (внутренняя элегантность),
рынок читает «ещё один оркестратор». Язык клина — язык боли рынка: *«не мержит, пока тесты
не зелёные, локально, на твоей подписке»*. Демо снимает cold-start («нечего индексировать,
нет плана, нет ключей»). Русскоязычное сообщество — реальный недоконкурентный плацдарм:
не переводить преимущество в машинный перевод, а вести две дорожки.

**Задачи.**
1. README hero: заголовок (RU/EN из тезиса выше) + таблица сравнения по 5 осям клина
   (локально / BYO-подписка / verify-гейт / мозг / граф) против Cursor Cloud / Codex /
   Conductor / Serena.
2. Встроенный demo-repo: маленькое работающее приложение с тестами и одной недостающей
   фичей; кнопка «Запустить демо» на welcome/пустой доске — план из 2 историй, одна
   пройдёт (зелёная), одна провалит verify (красная) — **главный кадр: красная полоса,
   которая не смержилась, рядом с зелёной, которая смержилась**.
3. Записать 3-минутное видео по сценарию (Приложение А); GIF-версия в README.
4. i18n UI: строки → простой словарь (без фреймворка), EN default + переключатель RU;
   EN-версия imba/README.
5. RU-дорожка: черновик поста на Habr по тому же демо.

**Критерий готовности.** Незнакомый разработчик по README за 60 секунд формулирует, что
это и чем отличается; демо от клика до красно-зелёного кадра < 5 минут; видео залито и
встроено.

**Риски.** Видео устаревает — переснимать по релизам; i18n держать простым словарём.

## Приложение А — сценарий 3-минутного демо

Весь ролик держится на одном визуальном такте: **красная полоса, которая НЕ смержилась,
рядом с зелёной, которая смержилась**.

- **0:00–0:20 — обещание.** Открыт flight-deck. Голос: «Это работает целиком на моей
  машине и моей Claude-подписке — ни API-счёта, ни кода наружу. Смотрите, чего оно
  *не сделает*». Индикаторы: Memory (размер графа), Brain (число фактов), Procedure.
- **0:20–0:50 — план на человеческом языке.** В демо-репо: «Добавь rate-limiting на
  логин». Планировщик (подпитан `brain.py recall`) предлагает две истории по разным
  файлам, у каждой — своя verify-команда (`pytest tests/test_login.py`). Принять.
- **0:50–1:40 — агенты по графу, не по grep.** Две полосы, Run. Два headless-агента в
  отдельных worktree, логи стримятся. Палец в лог: вызов `trace_path` — «он спрашивает
  граф 158 языков, *кто вызывает login()*, а не грепает».
- **1:40–2:20 — главный кадр.** Полоса A: тесты зелёные → вердикт COMPLETE. Полоса B:
  тесты **красные** → эскалация. Approve A → гейт перегоняет полный набор тестов уже в
  main-чекауте → merge → **квитанция** (дифф + команды + вердикт). Голос: «Смержилось
  потому, что тесты прошли *здесь, в main* — а не потому, что агент так сказал. Тот, что
  соврал, — остался за бортом». B висит несмерженной.
- **2:20–2:50 — память.** Вкладка Brain: новый урок отрефлексирован, счётчик фактов
  вырос. «В следующей сессии он это помнит — локально, без облака».
- **2:50–3:00 — число и тэглайн.** Metrics: сэкономленные токены, first-pass verify rate,
  time-to-green. «Локально. На твоей подписке. Мержит только зелёное. Это MindForge».
